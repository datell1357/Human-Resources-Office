# 영상과 같은 프로그램을 만드는 데 필요한 것

- 작성일: 2026-09-16
- 기준: [TTSOFT 프로그램 분석](../research/ttsoft-program-analysis.md)
- 상태: 개발 준비 검토안. 운영체제·지원 사이트·기술 스택은 아직 확정하지 않았으며 구현은 시작하지 않았다.
- 범위: 사이트 목록, 계정, 게시글, 가입·게시 작업, 결과 관리. 근태·급여·현장 배치 등의 사무소 내부 운영 기능은 별도 범위다.

## 1. 먼저 확보할 자료

| 필요한 자료 또는 결정 | 필요한 이유 | 처음 준비할 내용 |
| --- | --- | --- |
| 지원 사이트와 게시판 목록 | 각 사이트의 가입·로그인·작성 방식과 지원 가능 범위를 확인하기 위해 | 우선 검증할 대표 사이트 3~5곳의 URL, 게시판, 필요한 작업, 사용 가능한 공식 API 또는 자동화 허용 범위 |
| 테스트 계정과 시험 환경 | 정상 실행뿐 아니라 인증 만료·실패·권한 부족도 확인하기 위해 | 사용 권한이 있는 테스트 계정, 시험 게시가 가능한 공간, 계정 제공 방식. 비밀번호를 문서나 Git에 기록하지 않음 |
| 실제 게시글 예시 | 제목·본문·링크·이미지·파일·분류 등의 입력 계약을 정하기 위해 | 개인정보와 비밀정보를 제거한 대표 글 2~3개, 필수 서식, 링크·이미지 필요 여부 |
| 사용할 운영체제 | 설치 파일, 브라우저 배포, 보안 저장, 실행 검증 범위를 정하기 위해 | Windows 전용 / macOS 전용 / 두 운영체제 모두 |
| 운영 규모와 방식 | 로컬 저장과 중앙 서버, 동시 작업·권한 설계를 구분하기 위해 | 사용자 수, PC 수, 계정과 데이터 공유 여부, 대략적인 작업량, 예약 실행 필요 여부 |
| 실행·성공 기준 | 가입 성공, 등록 성공, 결과 열람 확인을 구분하기 위해 | 가입 자동화 필요 범위, 기존 계정 사용 방식, 게시 전 확인 단계, 게시 결과를 판정할 기준 |

영상에 나온 과거 목록과 작업 분모 206을 현재 지원 사이트 목록으로 사용할 수는 없다. 먼저 대표 사이트를 검증한 뒤 지원 대상을 늘리는 순서를 제안한다. 이것은 검증 순서이며 최종 지원 범위를 3~5개로 제한하는 결정은 아니다.

## 2. 만들어야 할 주요 구성요소

| 구성요소 | 필요한 기능 | 완료를 판단할 증거 |
| --- | --- | --- |
| 관리 화면 | 사이트·계정·게시글 목록, 검색·분류, 실행 설정, 상태 표시 | 사용자가 대상을 고르고 실제 작업을 시작·중지할 수 있음 |
| 사이트별 연동 | 각 대상의 지원 기능과 입력 규칙에 맞는 처리 | 공식 API 또는 허용된 브라우저 조작으로 대상별 시나리오를 검증함 |
| 계정·세션 관리 | 기존 계정 등록, 로그인 상태 확인·갱신, 계정별 세션 분리 | 만료·로그아웃·권한 부족을 구분하고 사람이 처리할 상태를 표시함 |
| 가입 처리 | 자동가입을 지원하는 대상의 가입 흐름과 사람 확인 단계 | 실제 가입 결과를 확인하고, 추가 인증·약관 동의 등이 필요하면 사용자에게 넘김 |
| 게시글 관리 | 제목·본문·서식·링크·필요한 첨부, 저장·불러오기·미리보기 | 저장한 내용이 대상 게시판에서 의도한 형태로 나타남 |
| 실행 관리 | 작업 목록, 순서, 간격, 시작·중지·재개, 실패 처리 | 중지 후 새로운 작업이 시작되지 않고 완료·미완료·불명확한 결과를 보존함 |
| 결과 관리 | 대상별 상태, 실패 원인, 게시글 링크, 결과 확인 | 등록 완료와 열람 확인을 구분하고 미확인 결과를 성공으로 처리하지 않음 |
| 로컬 저장과 보호 | 설정·작업 이력 보관, 비밀정보 보호, 백업·복구 | 재시작 후 상태가 유지되고 백업을 새 환경에 복원해 검증함 |
| 설치와 업데이트 | 실행 파일, 필요한 브라우저 런타임, 버전 호환성 관리 | 개발 도구가 없는 대상 OS에서 설치하고 실제 기능을 실행함 |

사이트 연동은 원본과 같은 화면을 만드는 것과 별도의 작업이다. 같은 게시판 엔진이어도 스킨, 필수 입력, 인증, 권한, 첨부 기능이 달라 개별 검증이 필요하다. 필요한 인력의 역할은 화면·데스크톱 개발, 사이트 연동·인증 처리, 테스트·배포로 나눌 수 있으며 한 개발자가 겸할 수 있다. 이후에도 사이트 변경 대응과 장애 확인을 맡을 사람이 필요하다.

## 3. 기술 구성 후보

Windows와 macOS를 모두 고려한 **후보**는 Electron + TypeScript + React + Playwright + SQLite다. 현재 저장소에는 기존 앱이나 패키지 구성이 없으며, 이 조합을 설치하거나 최종 채택한 것은 아니다.

| 용도 | 후보 | 선택 이유와 확인할 점 |
| --- | --- | --- |
| 데스크톱 앱 | Electron | 웹 기술로 Windows·macOS 등의 데스크톱 앱을 만들 수 있음. 설치 용량·메모리·업데이트 운영은 검증 필요. [공식 소개](https://www.electronjs.org/docs/latest/) |
| 화면과 코드 | React + TypeScript | 표·입력·상태 화면과 작업 데이터를 구성하기 위한 제안. React 자체가 필수인 것은 아님 |
| 브라우저 조작 | Playwright | 브라우저 작업을 제어하는 후보. 버전에 맞는 브라우저 바이너리가 필요하므로 설치·업데이트에 포함해야 함. [브라우저 문서](https://playwright.dev/docs/browsers) |
| 설정·작업 이력 | SQLite | 단일 PC의 앱 내부 저장에 적합한 후보. 여러 PC가 DB 파일을 직접 공유하는 구성과 구분해야 함. [적합한 사용 사례](https://www.sqlite.org/whentouse.html) |
| 비밀정보 저장 | 운영체제 보안 기능, Electron safeStorage 검토 | OS가 제공하는 암호화 기능을 활용하는 후보. 플랫폼별 보호 범위와 사용 가능 여부, 복원 방법을 검증해야 함. [safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage) |

공식 게시 API가 제공되고 사용 권한이 있다면 해당 연동을 먼저 검토한다. Playwright를 채택했다고 모든 사이트의 가입·게시를 지원하게 되는 것은 아니다. 사이트 조사와 연동 구현은 여전히 필요하다.

로그인 상태 파일에는 계정을 대신 사용할 수 있는 쿠키·헤더가 포함될 수 있으므로 코드 저장소와 분리하고 보호해야 한다. 비밀번호뿐 아니라 세션 파일·진단 로그·실패 화면에도 같은 기준을 적용한다. [Playwright 인증 문서](https://playwright.dev/docs/auth)

## 4. 서버와 외부 서비스가 필요한 조건

| 운영 형태 | 필요한 환경 |
| --- | --- |
| 한 PC에서 한 사람이 사용 | 앱이 실행될 PC, 인터넷 연결, 대상 사이트 접근 권한, 로컬 저장소와 백업 위치. 별도 애플리케이션 서버 없이 설계 가능 |
| 로컬에서 예약 실행 | 예약 시각에 PC와 실행 프로세스가 동작해야 함. 절전·재부팅·앱 종료 후의 동작 규칙 필요 |
| 여러 PC에서 계정·작업·결과 공유 | 중앙 API, 사용자 인증·권한, 서버 데이터베이스, 충돌·동시 실행 관리와 운영 백업 |
| PC가 꺼져 있어도 상시 실행 | 항상 켜진 실행 장비 또는 서버와 작업 상태를 확인할 관리 경로 |
| 다른 사용자에게 배포·판매 | 설치·서명·업데이트·문의 대응. 선택한 판매 방식에 따라 라이선스 서버·결제·고객 관리 추가 |
| AI로 글 초안 작성 | 선택 기능. 도입할 때 모델·API 또는 로컬 모델, 비용·데이터 처리 기준을 별도로 결정 |

지금 단계에서 특정 유료 서비스나 서버 상품을 구매할 필요는 확정되지 않았다. 운영 형태가 정해진 뒤 필요한 항목만 산정한다. 자동가입에 본인 확인·문자·이메일 확인·CAPTCHA가 있으면 자동화 가능 범위와 사용자 직접 처리 단계를 구분해야 한다.

## 5. 개발과 검증의 권장 순서

1. **대상 조사:** 대표 사이트, OS, 게시글 샘플을 확보하고 각 사이트의 지원 가능 작업을 기록한다.
2. **공통 기능:** 목록·글 편집·저장·실행 상태·로그·중지 화면을 만들고 시험 환경에서 연결한다.
3. **대표 대상 검증:** 가입이 필요한 대상과 기존 계정을 사용하는 대상의 흐름을 각각 검증한다. 추가 인증은 사람이 완료할 수 있어야 한다.
4. **실패·재개 검증:** 인증 만료, 네트워크 중단, 게시 후 응답 유실, 중지·재시작을 확인한다. 게시 성공 여부가 불명확한 경우 먼저 결과를 확인하고 중복 제출을 방지한다.
5. **배포 검증과 확대:** 목표 OS의 설치본에서 실제로 실행하고, 백업 복원·업데이트를 검증한 뒤 사이트별 지원을 확대한다.

첫 사용 가능한 버전의 완료 조건은 사용자가 선택한 대표 대상에 대해 **준비 → 실행 → 결과 확인 → 실패·중지 처리 → 재시작 후 기록 유지**가 실제로 동작하는 것이다. 영상과 비슷한 화면이 보이는 것만으로 완료로 판단하지 않는다.

## 6. 비용과 일정 산정에 영향을 주는 것

개발량은 사이트 수뿐 아니라 서로 다른 인증 방식·편집기·첨부 형식의 수, 자동가입 필요 여부, 대상 OS, 공유·예약·판매 기능에 따라 달라진다. 대표 사이트를 조사하기 전에는 신뢰할 만한 일정이나 비용을 확정할 수 없다.

초기에는 **사용할 OS, 우선 지원 사이트 3~5곳, 게시글 예시, 개인용 또는 여러 사람이 쓰는 제품인지** 네 가지가 정해지면 구체적인 범위와 개발 순서를 정할 수 있다. 테스트 계정은 공개 문서·커밋에 넣지 않고 실제 연동을 검증하는 단계에서 안전하게 준비한다.
